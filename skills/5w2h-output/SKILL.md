# 按 5W2H 输出

要解决的问题是**输出太长、看不完**。7 格是套在回答外面的壳——把一大段话切成七个能扫的格子。**七格本身不是完整性考核表。**

**可读性优先于完整性。** 两者冲突时：砍内容、留「待定」，不要扩写。

## 写成什么样

- 开头一句话结论（30 字内），然后七个带小标题的格子，顺序固定。
- **每格一句话，最多两句。** 目标 200 字上下；超过 300 字就说明你在扩写。
- 没有信息的格子写「不适用」或「待定（谁给）」，一句话带过，绝不硬编。
- 不复述用户已知的背景，不写「首先 / 其次 / 综上所述」，不解释自己为什么这么排版。

## 七格

| 格 | 写什么 | 最容易写成废话的地方 |
| --- | --- | --- |
| **What** | 做什么、**不做什么** | 只写做什么，不写边界。不写「不做什么」，范围就会在动手后膨胀 |
| **Why** | 为什么现在做、不做会怎样 | 「提升效率 / 优化体验」这种放哪都成立的话，等于没说 |
| **Who** | 谁执行、谁拍板、谁被影响 | 只写执行者，漏掉决策人和被影响的人 |
| **When** | 什么时候要、卡在谁身上 | 只写 deadline，漏掉「依赖别人给东西」的时间点 |
| **Where** | 在哪做、在哪生效 | 漏掉运行环境 / 适用场景 / 不适用场景 |
| **How** | 怎么走、分几步、每步的完成标准 | 只有目标没有路径，或路径没有可验证的「做完了」判据 |
| **How much** | 量级：成本、工期、规模、**验收标准** | 被误解成「多少钱」。它问的是量级和边界——多少算够、多少算超 |

右边这列是**每格最容易膨胀成废话的方式**，写的时候对着躲。

## 三条硬规则

1. **自己先查，不要反问。** 现状、代码、历史、已有文档，自己去看。唯一例外：某格答错会推翻整篇（通常是 Why 和谁拍板）时，问**一句**，然后停下等回答。
2. **拿不到的写「待定」，绝不编。** 编出来的工期、预算、日期比空着危险得多——它会被人当真。待定要写清需要谁给什么。
3. **短了不加字，缺了不掩饰。** 别为了凑满七格注水，也别为了好看把没查到的东西说死。

## 流程

1. 先判断该不该做：只是问事实、要代码、闲聊 → 直接答，不启动本流程。
2. 能查的自己查；查不到的留「待定」。
3. 按七格写短。
4. 只有正式文档才落盘：先问放哪（跟仓库现有约定走）再写文件；否则直接在对话里给出。

## 收尾

只在**确实存在**待定或推断时补一行：「待定：X（需要谁给）；推断：Y（依据 Z）」。全都由事实支撑就省掉这行——它也算长度。

## 不适用

- 只是问事实 / 要代码 / 闲聊 → 直接答。
- 在做**创意发散**（还没定要做什么）→ 先去探索，别急着套七格。
- 想**拷问已有计划**的漏洞 → 那是 grilling 的活。
